# P7500 네이티브 NV 백엔드

`native_nv.c`는 가상 소비량·시리얼 세대를 기존 NV 서비스에 연결한다.
원본 ARM API의 인수 검증, 요청 전송, 완료 대기까지 실행해 시험했다.
**실제 프린터의 플래시 작업자·가비지 수집·전원 차단 시험은 아직 수행하지 않았다.**
부팅 훅과 코드·컨텍스트 RAM 배치를 적용한 IC13/IC14 BIN도 생성하지 않았다.

## 연결한 API와 초기화 순서

| 항목 | 원본 위치 또는 값 |
|---|---|
| 동기 NV 읽기 | 0x435EFDD4 |
| 동기 NV 쓰기 | 0x435EFDF0 |
| NV 설정표 | 0x43740E74, 157행, 행당 20바이트 |
| 네이티브 배치 생성기 | 0x435F364C |
| 인수 검증 가드 진입점 | 0x435F3274 |
| 생성된 ID 매핑표 | 0xB9A5802C, 행당 12바이트 |
| 소유자 기록 A/B | 0x01607500 / 0x01607501 |

먼저 0x435F3274의 PC 독립적인 첫 두 명령을 검증·재배치한 트램펄린을
`vr_nv_guard_attach()`에 전달하고 원본 진입점을 `vr_nv_guard`로 연결해야 한다.
가드는 원래 검증을 실행한 후 아래의 인덱스 경계를 추가 검사한다.
가드가 설치되지 않으면 P7500용 등록·백엔드 연결 함수는 실패한다.

1. 네이티브 NV 배치 생성 **전**, `vr_nv_p7500_register_owner()`로 소유자 기록을
   등록한다. 이 함수는 원본 세 중복 행의 ID·크기·권한과 새 ID 충돌 여부를 확인한다.
   맞지 않으면 수정하지 않고 실패한다. 이미 같은 소유자 등록이면 그대로 성공한다.
2. 원래 NV 초기화 흐름에서 배치 생성기가 새 설정표로 ID 매핑을 만든다. 실행 중인
   NV 서비스의 매핑표를 임의로 다시 만드는 용도로 사용해서는 안 된다.
3. 호출자가 충돌 없는 공간에 확보한 `vr_nv_backend`와 native 단위의 12슬롯 용량을
   `vr_nv_p7500_init()`에 넘겨 `vr_io`를 만든다. 이 함수는 생성된 소유자 ID·그룹·간격을
   검사한다. 설정표만 바꾸고 매핑표를 갱신하지 않은 경우에는 연결하지 않는다.
4. `vr_init()`으로 기존 상태를 복원한다. 이후 네이티브 어댑터를 연결한다.
   NV API는 완료 메시지를 기다리므로 NV 작업자 자신의 문맥에서 호출하면 안 된다.
   호출은 CSIC 측 디스패처에서 직렬화해야 한다.

새 소유자 설치에서 기록을 만들 때만 `vr_nv_install_empty_records()`를 명시적으로
호출할 수 있다. 이 작업은 두 소유자 기록을 FF로 다시 쓰며 **기존 가상 소비량과
세대를 지운다.** 실행 중인 코어를 중지한 설치 단계에서만 사용하고, 완료 후
`vr_init()` → `VR_EMPTY` 확인 → `vr_format_empty()` 순서로 새 상태를 만든다.
일반 부팅·읽기 오류·손상 복구에서는 호출하지 않는다. 백엔드는 기록 누락이나
읽기 실패를 빈 저장소로 해석하지 않으며, 자동 초기화 경로도 없다.

이 순서는 통합 코드가 충족해야 할 계약이다. 현재 실제 부팅 지점에 설치한
호출 순서나 실제 RAM 배치가 아니다. 개인키·업데이트 서명 검증은 변경하지 않는다.

## 기존 배치를 유지하는 등록

원본 설정표 120/121/122행에는 같은 ID 0x01600945, 레코드 크기 1, 개수 10이
있다. 원본 검증·주소 조회 루틴은 ID를 처음 찾는 행을 선택한다. 첫 행은 보존하고
뒤의 두 행에 소유자 ID를 넣는다. 기존 레코드의 공간은 `(2 + 12) × 10 = 140`바이트,
새 레코드는 `(128 + 12) × 1 = 140`바이트다. 2는 홀수 길이를 짝수로 올린 값이고
12는 원본 생성기가 사용하는 레코드 부가 공간이다.

`probe_native_nv.py`가 원본 ARM 배치 생성기를 변경 전후 실행하여 다음을 확인한다.

- 나머지 155행의 ID·주소·그룹 값 유지
- 두 소유자 행의 주소와 그룹 유지, ID만 변경
- 29개 볼륨의 생성된 배치 구조 전체 유지

새 raw NVRAM 주소를 할당하거나 DSM 미러 0x29를 덮어쓰지 않는다. 일반 ID 조회에서
중복된 행을 활용하는 변경이며, 전체 항목을 열거하는 진단·백업 출력에는 새 ID가
나타날 수 있다. 상위 모듈에는 0x01600946/0x01600947의 메타데이터도 있으므로,
실제 부팅 중 설정표가 교정되는지도 확인해야 한다. 교정되어 원본 세 중복 행과
다르면 현재 등록 함수는 거부한다. 플래시 서비스 내부의 유지보수·마모·전원 차단
계약 검증은 별개다.

원본 검증기는 개수 10인 기존 항목에서 인덱스 10도 허용하고, 주소 조회기는 그
인덱스를 다음 행으로 계산한다. 원본 ARM으로 이 주소가 소유자 A와 겹치는 것을
재현했다. 따라서 배치 유지 확인만으로 이 두 행을 전용해서는 안 된다. 가드는
기존 항목의 정상 인덱스 0~9는 유지하고 10 이상을 거부한다. 소유자 A/B도 원본
검증기가 인덱스 1을 허용하므로, 가드에서 유일한 인덱스 0으로 제한한다.
원본·가드 양쪽의 읽기/쓰기 검증 결과를 비교해 이 경계 차단을 확인했다.

## 128바이트 형식과 커밋

| 위치 | 내용 |
|---|---|
| 0..3 | 형식 `V7C1` |
| 4..11 | 64비트 트랜잭션 순번 |
| 12..119 | 12슬롯 × 소비량 40비트 + 세대 32비트 |
| 120..123 | CRC-32; 외부에서 공급한 용량 배열도 검사값에 결합 |
| 124..127 | 미커밋 FF 또는 최종 커밋 표식 |

코어의 기존 512바이트 v1 정규 기록을 손실 없이 변환한다. 용량은 native 설정에서
다시 공급하지만 CRC에 결합되므로 다른 용량으로 잘못 복원하지 않는다. 알 수 없는
v1 확장 데이터를 조용히 버리지 않도록 정규 형식인지도 확인한다.

`erase/write` 콜백은 RAM 스테이징만 갱신한다. `sync`에서 128바이트를 네이티브
동기 API로 기록하고 완료 상태가 0인지 확인한 뒤, 동일 API로 재독출·비교한다.
코어의 미커밋 본문과 최종 표식은 각각 별도 동기화로 저장한다. 완료 결과가
불명확하면 백엔드 장애를 고정하고 재초기화 전의 추가 I/O를 거부한다.

명령 전송 성공만으로 코어 상태를 바꾸지 않는다. 기록 완료 후 오류 응답이 온
경우에도 정상 처리로 넘기지 않고, 재시작 때 실제 유효 기록으로 상태를 결정한다.
이전 기록으로의 손상 복원은 마지막 트랜잭션을 되돌릴 수 있다는 기존 한계가 있다.

두 논리 기록의 물리 소거·압축·이동은 원래 NV 서비스에 맡긴다. 두 기록은 같은
네이티브 저장 서비스에 있으므로, 서비스의 가비지 수집이 정전에도 두 기록을
보호하는지는 실기 및 하위 작업자 시험이 필요하다. 원본 API 완료 응답만으로 그
물리 보장을 검증했다고 주장하지 않는다. 소비량 갱신마다 저장하는 현재 방식의
쓰기 빈도와 마모도 실기에서 평가해야 한다.

## 검증 범위

`test_native_nv.py`는 컴파일한 C 브리지에서 형식 경계 30건, 논리 기록 쓰기 중단
257곳, compact 기록 비트 손상 1,024건, 용량 불일치, ID 충돌, 오류·미래 형식 보존과
명시적 설치 초기화를 확인한다. 쓰기 중단은 NV 논리 기록 전송 모델의 바이트별
중단이며 실제 NOR 소거나 가비지 수집 중단 시험이 아니다.

`probe_native_nv.py`는 컴파일한 ARM 백엔드에서 원본 NV API를 실제 실행한다.
OS 메시지·메모리 함수와 물리 NV 작업자는 파일 기반 시험 대역이다. 파일과 디렉터리를
fsync한 뒤 완료 응답을 보내며, 새 ARM 인스턴스로 13개 프로필을 복원한다.
대기 중 코어 상태 미공개, 완료 오류, 저장 후 오류의 재시작 정합성, 매핑표 불일치
거부, 기록 누락 시 자동 초기화 금지와 별도 설치 초기화를 검사한다.

전체 재현은 `python3 runtime/verify.py`로 실행한다. 결과는 `analysis/`에, 소스와
함께 검토할 마지막 실행 결과는 `validation/`에 둔다.
