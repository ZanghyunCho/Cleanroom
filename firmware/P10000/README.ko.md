# SC-P10000 인증 경로 비교 연구

이 디렉터리는 사용자 제공 FM001PA EFU와 FM018GB SPI NOR 덤프를 분석한 재현 코드와 검증 기록이다. 두 펌웨어 버전은 다르며 서로의 완성 SPI 이미지를 혼합하지 않는다. 클라우드에서는 실기 시험을 수행하지 않았다. 2026-11-04 사용자는 시험용 EFU 적용 성공과 메인터넌스 가용 공간 100% 표시를 보고했다. 잉크 카트리지 가상화와 전원 차단 복구 시험은 미검증이다. 상세 기록은 `validation/user-reported-maintenance-success.json`에 있다. `LAB_UNVERIFIED` 파일은 연구용 산출물이다.

## 현재 판단

인증 코드를 고치기 전에 **대상 블록의 메타데이터 플래그만 변경하는 경로를 먼저 검토할 근거가 생겼다.** 원본 업데이터와 부트 코드에는 인증 여부를 메타데이터로 결정하는 분기가 존재한다. 원본 ARM 코드를 실행해 그 분기를 확인했다. 이는 원본 MAC 재생성이나 EFU 전체 수신 성공을 입증한 결과는 아니다.

여기서 ‘인증 코드 무수정’은 사용량 조회 함수를 수정하지 않는다는 뜻이 아니다. 두 방식 모두 해당 함수 첫 8바이트를 변경하며, 인증 검사 함수의 기계어 변경 여부가 다르다.

| 비교 | 메타데이터 방식 | 대상 부트 코드 변경 방식 |
| --- | --- | --- |
| FM018GB 사용량 조회 함수 | `0x13954`의 8바이트 변경 | 동일 |
| 대상 내부 헤더 `+0x20` | 인증 플래그 1 → 0 | 1 유지 |
| 원본 부트 코드 | 처음 128 KiB 그대로 유지 | 한 분기와 16바이트 코드 추가 |
| 다른 블록 인증 분기 | 유지 | 유지 |
| 대상의 실제 MAC 재계산 | 하지 않음 | 하지 않음 |
| 원본 ARM 압축 해제기 전체 출력 | 의도한 수정본과 일치 | 의도한 수정본과 일치 |
| 실기 부팅 | 미검증 | 미검증 |

FM001PA EFU에는 외부 레코드와 내부 헤더의 인증 플래그를 모두 0으로 바꾼 시험 후보를 별도로 만들었다. 업데이터 코드, 다른 네 구성요소 및 ZIP의 나머지 리소스 내용은 보존한다. NML 마지막 32바이트의 의미와 전체 수신 경로의 해석은 미해결이다. 이후 사용자는 자신의 장비에서 이 후보의 적용 성공을 보고했다. 이는 다른 장비·버전의 호환성까지 입증하지 않는다.

## 원본 코드에서 확인한 내용

- FI22E1 업데이터 인증 게이트: `0x38009ffc`. 외부 레코드 플래그가 1일 때 내부 플래그 1을 요구하고 MAC 검사를 호출한다. 외부 플래그 0이면 이 검사를 건너뛴다.
- 별도 바이트 합계 게이트: `0x3800a798`. 인증 플래그를 꺼도 합계가 틀리면 거부한다.
- FB22E1 부트 인증 게이트: `0x1878`. 부트 모드 1에서 내부 헤더 플래그가 1인 블록의 MAC을 확인한다. 모든 부트 모드에서 같은 경로를 따른다고 입증하지는 않았다.
- 원본 MAC 루틴 `0x3800208c`는 공개 시험 벡터 세 개에서 표준 HMAC-SHA1과 일치한다.
- 모델 `0x807`의 파생 키 계산은 공개 합성 20바이트 재료로 원본 ARM과 Python 구현이 일치했다. **실제 키 재료의 주소 매핑과 원본 MAC 재현은 아직 성공하지 않았다.**
- 원본 부트 로더 `0x17e8`과 LZSS 디코더 `0x4e44`를 실행해 수정 모듈 전체를 복원했다. 전체 바이트와 원본 코드의 복원 후 바이트 합계 검사를 확인했다.
- 사용량 조회는 0, 여유량 계산은 688,000,000을 반환하는 70개 호출을 각 후보에서 확인했다. 실제 유지보수 배출량이나 물리적 탱크 상태에 대한 시험은 아니다.

게이트 시험에서 변경하지 않은 다른 블록의 MAC 호출은 **입력과 태그가 원본과 동일한지 확인하는 대조 함수(oracle)** 로 대체했다. 이 대조는 인증 분기와 다른 블록의 거부 동작을 시험하기 위한 것이다. 실제 비밀 키를 사용한 암호 검증으로 해석하면 안 된다. 반면 원본 LZSS 디코더·복원 합계·사용량 함수 실행에는 이 MAC 대조 함수를 사용하지 않았다.

## 산출물과 버전

`build/`는 Git에서 제외한다. 사용자 설정이 포함될 수 있는 원본 덤프, IC7 및 개인키는 이 디렉터리에 공개하지 않는다.

- `LAB_UNVERIFIED_FM001PA_METADATA_ONLY.EFU`: FM001PA 전용 EFU 시험 후보. 대상 재압축 스트림은 18바이트 증가한다. 외부 레코드, 내부 압축·복원 합계, NML 길이·합계 및 RCX 선언 길이를 수정했다. 마지막 불명 32바이트는 원본 그대로이며 유효성 미검증이다.
- `LAB_UNVERIFIED_FM018GB_metadata-only_IC2.BIN`, `..._IC3.BIN`: 제공된 FM018GB 덤프 기반. 대상 블록과 그 헤더만 변경한다.
- `LAB_UNVERIFIED_FM018GB_targeted-boot-code_IC2.BIN`, `..._IC3.BIN`: 비교용 부트 코드 변경 후보. `0x18b4`에서 `0x1ff00`으로 분기하고 대상 주소 `0x1400000`만 건너뛴다. 부트 합계 `0x1fff0`을 다시 계산한다.

정확한 파일 크기·SHA-256·허용 변경 범위는 `validation/` 보고서에 기록한다. IC2/IC3 분할·재병합의 전체 일치도 확인한다. 원본 W25Q128BV는 SPI NOR이며 NAND/OOB/ECC 덤프로 취급하지 않는다. `inputs/nand-dump`라는 기존 폴더명만 유지했다.

## 재현

Python 3와 Unicorn 2가 필요하다. 실행기는 기존 `../P7500/tools`의 Python 모듈 경로도 사용한다. `inputs`는 비공개 분석 자료 경로에 연결한다. 입력 구조는 각 스크립트의 경로를 참고한다. 두 빌더는 기준 원본 SHA-256을 확인한다.

```sh
python firmware/P10000/probe_hmac_vectors.py
python firmware/P10000/probe_gates.py
python firmware/P10000/probe_key_mappings.py
python firmware/P10000/build_spi_research.py
python firmware/P10000/build_efu_research.py
```

주소 매핑 탐색은 제공된 파일의 마스크·주소 폭·워드 순서 가설만 시험한다. 임의 비밀 키 공간을 탐색하지 않는다. 혼합 매핑 탐색은 시간 제한으로 두 구간으로 나눴다.

```sh
python firmware/P10000/probe_mixed_mappings.py
python firmware/P10000/probe_mixed_mappings.py --start-index 347332 --seconds 180
```

이번 기록에서는 0~347331 및 347332~521639를 이어서 총 521,640개 조합을 빠짐없이 확인했으며 일치 MAC은 0개였다. 단일 파일 공통 매핑 986개 가설에서도 일치하지 않았다.

기본 실행의 종료 인덱스는 실행 속도에 따라 달라진다. 재실행할 때에는 해당 보고서의 종료 인덱스부터 이어야 하며, 두 구간을 겹치거나 빠뜨린 채 전체 탐색 완료로 판정하지 않는다.

## 남은 불확실성

1. NML 끝의 불명 32바이트와 앞단 수신 서비스가 변경된 패키지를 받아들이는지 확인해야 한다. ZIP CRC와 설치 내부 검사 통과만으로는 이를 판단할 수 없다.
2. 부트 모드 선택, 실제 메모리 배치, 플래시 기록, 다른 프로세서·FPGA 및 주변장치 초기화는 현재 단위 실행의 범위 밖이다.
3. 외부 주소 다섯 곳의 실제 키 재료를 제공된 IC 덤프에서 읽는 방법은 아직 찾지 못했다. 매핑 가설 실패는 키가 덤프에 없다는 증명이 아니다.
4. 사용량 반환을 0으로 만들더라도 유지보수 관련 모든 상태·오류·칩 통신이 가상화되는 것은 아니다.

현재 증거에서는 부트 코드 변경을 늘릴 이유보다 메타데이터 경로를 우선 조사할 이유가 더 크다. 다만 실기 검증 전에는 어느 후보도 정상 부팅을 보장하지 않는다.
