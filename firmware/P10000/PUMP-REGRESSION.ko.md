# SC-P10000 V4.5 — ILS 원본 복원 진단 후보

V2를 기준으로 제어 변경을 분리하는 후속 진단 EFU 3종을 로컬 빌드했습니다. [제어 변경 분리 진단](CONTROL-ISOLATION.ko.md)에 변경 범위·실기 비교 순서·한계를 기록합니다. 아직 원인 확정이나 실기 성공을 의미하지 않습니다.

## V4.5 실기 결과 및 후속 조사

사용자는 V4.5에서도 인쇄 전 필요한 시점에 감압 펌프가 시작하지 않았다고 보고했습니다. V2는 같은 카트리지·공급·용지 조건에서 정상입니다. 사용자 관찰 순서는 **펌프 미동작 → 프린터 재시도 → 용지 위치 어긋남 → 용지 감지 오류**입니다. 따라서 이 보고에서 용지 오류를 일차 원인으로 취급하지 않습니다. ILS 조회 8바이트 복원만으로는 회귀가 해결되지 않았습니다.

원본 작업 허용 함수 `0x43c28f98`를 원본·V2·V4.5에서 각각 실행했습니다. 동일한 제어 상태를 주면 세 버전 모두 정상 1건과 잉크 10슬롯/유지보수 2슬롯의 개별 비정상 12건에서 동일하게 동작했습니다(총 39건). 호출 성공 반환값은 1이어도 별도 출력의 작업 허용 값은 0일 수 있습니다. 따라서 호출 성공이나 화면 잔량만으로 인쇄 준비 완료를 판정하면 안 됩니다.

이 시험은 원본 초기화 데이터 영역을 복사하되, 슬롯 선택·가용 상태와 모드 바이트를 명시적으로 주입하고 로그/오류 기록을 대체합니다. 실기 상태나 상태 생산 경로를 재현한 시험은 아닙니다. `probe_operation_gate.py`와 `validation/operation-gate-fixtures.json`에 범위와 결과를 기록했습니다. 아직 실기의 실패 원인은 확정하지 못했습니다. V3에서 생략한 원본 초기화·상태 갱신과 RTOS 완료 경로가 다음 조사 대상입니다. 펌프 강제 허용이나 새 EFU는 이 시험으로 정당화되지 않습니다.

## 후속 조사: 실제 응답 연결 및 항상 장착됨 응답의 충돌

추가 시험에서는 슬롯 가용 결과를 상위 함수에 직접 주입하지 않고 다음 원본 ARM 경로를 연결했습니다.

`V4.5 잉크/유지보수 power 함수 → CSIC 요청 처리기 → CSIC API → IKS 상태 갱신 → 작업 허용 판정`

가용 조회 요청 `0xbc000013`은 원본 처리기 `0x43b15a60`, 원본 API `0x43b349d4`, IKS 함수 `0x43c13b8c`/`0x43c2a634`를 거칩니다. 최상위 `0x43c2ff58`의 출력 객체 `+0x28`에서 허용 여부를 확인했습니다. 정상 분기에서는 V4.5 실제 처리기가 12개 가용 플래그를 모두 1로 반환하고 요청도 완료하며, 최상위 출력은 1입니다. 이 조건에서 단순 가용 응답 누락 가설은 재현되지 않았습니다.

원본 `0x43c2a8bc`는 `0x7ff029c2`를 읽으며 로그에서 이를 `洗浄排出カウンター`(세정 배출 카운터)라고 부릅니다. 이 값이 1~5인 분기에서는 장착 여부 조회 `0xbc000014`도 수행합니다. 원본 처리기 `0x43b158a4`가 V4.5의 가상 장착 함수 `0x43b1b328`을 호출하고, 원본 API `0x43b34818`로 전달합니다. 원본 판정은 해당 분기에 지정된 슬롯에 카트리지가 장착되어 있으면 작업을 허용하지 않습니다.

| 카운터 시험 입력 | V4.5 장착 응답 | 장착 응답만 모두 0으로 대체한 대조군 |
| --- | --- | --- |
| 0 | 작업 허용 1 | 작업 허용 1 |
| 1~5 각각 | 작업 허용 0, 내부 오류 기록 `0x23` | 작업 허용 1 |

총 12건을 실제 ARM 코드로 실행했습니다. `0x23`은 시험에서 오류 기록 함수에 전달된 내부 값이며, 실기 화면의 오류 코드로 확인된 것이 아닙니다. **항상 장착됨 응답이 원본 세정 작업 상태와 충돌할 수 있다는 구체적인 반례**입니다. 실기의 카운터 값은 모르므로 이번 펌프 회귀의 원인으로 확정할 수 없습니다. 카운터 0에서는 문제가 재현되지 않는다는 대조 결과도 함께 유지합니다. 카운터를 강제로 0으로 지우는 수정은 하지 않았습니다.

시험은 별도 두 CPU 인스턴스로 요청/응답을 주고받으며 RTOS 전달만 동기식으로 대체합니다. 원본 초기화 데이터/저주소 코드/SRAM을 복사하지만 전체 부팅은 실행하지 않습니다. 슬롯 선택과 슬롯 대응표는 명시적인 시험 입력이고, NV/날짜 후처리 두 함수는 대체했으며 JCT 상태 통지와 최종 IKS 응답 전달은 실행하지 않습니다. 부재 대조군은 실제 칩 검출 결과가 아니라 장착 조회 출력만 0으로 바꾼 시험입니다. 원본 전체 V2와의 실기 비교 또는 실제 펌프 제어 검증으로 해석하면 안 됩니다.

재현: `python firmware/P10000/probe_ink_operation_bridge.py`

결과: `validation/ink-operation-bridge.json`

수정 방향은 카트리지 정보 표시와 기구 제어용 삽입/제거 절차를 구분하고 원본 작업 상태 전이를 보존하는 것입니다. 현재의 모든 호출에 대한 장착/정상 상수 반환은 이 반례를 처리하지 못합니다. 아직 새 EFU로 배포하지 않았습니다.

## 후속 조사: 감압·흡입 공급 요청에서 역추적

앞의 세정 분기는 Ink Eject 같은 서비스 작업에 사용될 가능성이 있으나 메뉴 명령에서의 호출 관계는 아직 확인하지 못했습니다. 일반 인쇄 펌프 회귀의 원인으로 채택하지 않습니다.

다음 경로를 원본 명령으로 확인했습니다.

- IKS 흡입 공급 함수 `0x43c2278c`가 공급 요청을 구성합니다. 슬롯 선택 정보, 반복 횟수, 종료 검출 사용 여부와 구동 방식이 별도 입력입니다.
- API `0x43b3e374`는 명령 `0x9c000005`에 잉크 10슬롯 선택 마스크(`+0x26`), 반복 횟수(`+0x1e`), 검출 옵션(`+0x3a`), 구동 방식(`+0x3c`)을 담습니다.
- 원본 수신 처리의 `0x43c7c2f4` 분기가 이를 꺼내 `0x43b9af90`으로 전달합니다. 이 드라이버의 관련 본문은 원본·V2·V4.5가 바이트 단위로 동일합니다.
- `0x43b9af90`은 반복 횟수가 0이면 구동 요청 없이 반환합니다. 횟수가 양수여도 공통 상태 워드 `0x43e86018`의 `0x100` 비트가 설정되면 반환합니다. 이 비트의 실기 설정 원인은 아직 미확정입니다.
- 두 조건을 통과하면 `0x43b96764`로 모션 단계 구동을 요청하고 `0x43b934a0`을 거칩니다. 검출 옵션이 1이면 **그 이후** `0x43b33e48`로 CSIC 잉크 종료 결과를 조회합니다.

원본·V2·V4.5에서 횟수 0/1/2, 정지 비트 해제/설정, 종료 응답 0/1을 조합한 총 36건을 실행했습니다. 실제 모터 호출과 대기·콜백은 가로채고, CSIC 응답도 명시적인 시험 입력으로 대체했습니다.

| 입력 조건 | 관찰한 모션 요청 |
| --- | --- |
| 횟수 0 | 없음 |
| 횟수 양수, 정지 비트 설정 | 없음 |
| 횟수 1, 정지 비트 해제 | 종료 응답 0/1 모두 첫 구동 요청 발생 |
| 횟수 2, 정지 비트 해제, 종료 응답 0 | 두 반복 실행 |
| 횟수 2, 정지 비트 해제, 종료 응답 1 | 첫 반복 후 중단 |

따라서 **이 경로에 요청이 정상적으로 도달했다면**, 종료 응답을 0으로 만드는 변경만으로 첫 모션 요청이 사라지는 현상은 재현되지 않습니다. 이 응답은 첫 구동 이후 반복 중단 여부에 영향을 주었습니다. ILS 조회만 복원한 V4.5에서도 실기 증상이 남았다는 보고와 함께, ILS 상수화만을 일차 원인으로 보는 근거는 약해졌습니다. 다른 경로와의 상호작용까지 배제한 결론은 아닙니다.

다음에 구분해야 할 것은 상위 작업에서 요청 자체가 생성되지 않는지, 횟수가 0인지, 공통 정지 비트로 차단되는지, 모션 요청 이후 실제 하드웨어가 동작하지 않는지입니다. 실기에서 이 입력과 실행 지점을 관찰하지 못했으므로 어느 경우인지 확정할 수 없습니다. 임의로 반복 횟수를 올리거나 정지 비트를 지우는 수정은 하지 않았습니다.

재현: `python firmware/P10000/probe_pressure_request.py`

결과: `validation/pressure-request-trace.json`

**V4.5는 배포 식별 이름이며, 펌프 문제 해결판으로 검증된 것은 아닙니다.** V2는 정상이고 V3 이후 인쇄·헤드 청소·자동 노즐 검사가 안 되며, 현재 V4에서 ‘용지를 감지하지 못했습니다’ 오류와 펌프 미동작이 보고됐습니다. 기존 일반 동작/표시 성공 보고를 실제 인쇄 동작 성공으로 해석하면 안 됩니다.

이번 진단 후보는 **현재 설치 버전인 공개 V4를 기준으로**, 모듈 오프셋 `0x3f3a4`의 ILS 조회 첫 8바이트만 원본으로 복원합니다. 나머지 압축 해제 모듈은 V4와 동일합니다. 원시 디바운스 값이 그대로 조회 결과로 나오는 15개 시험을 통과했습니다. 펌프·용지 감지 인터록을 강제로 허용하거나 펌프를 강제 구동하는 코드는 넣지 않았습니다.

V3/V4에는 별도 메타데이터 결함도 확인됐습니다. 순중량 필드 680과 정격 용량 필드를 혼동했으며, 원본 클래스 2 파서는 각각 680과 700을 기록합니다. 원본 30개 경우 및 별도 수정 코드 회귀 시험으로 확인했습니다. **변수를 섞지 않기 위해 이 700 수정은 이번 ILS 진단 EFU에 포함하지 않았습니다.**

## 목적과 확인

정상 기준은 기존 V2입니다. 프린터를 정상 사용해야 한다면 먼저 V2로 돌아가세요. 이 진단 파일은 동일한 용지·카트리지 상태·실제 잉크 공급 조건에서 V4와 비교해 ILS 상수화의 관여 여부를 분리하기 위한 후보입니다.

- 이 후보에서 증상이 해소되면 ILS 조회 변경의 관여를 조사할 근거가 됩니다. 모든 V3 변경이 올바르다는 뜻은 아닙니다.
- 증상이 계속되면 ILS 변경 단독으로 설명할 수 없습니다. 다른 V3 가상화 변경과 상위 작업 허용 조건을 이어서 조사해야 합니다.
- 후속 사용자 관찰에서는 펌프 미동작이 먼저이고 용지 감지 오류는 재시도 후 발생했습니다. 위 실기 결과를 우선합니다.

실제 잉크 공급과 폐잉크 수거 경로를 유지하세요. 공급이 없는 상태에서 인쇄·청소를 반복하거나 강제 펌프 구동을 하지 마세요. 정확한 오류 문구/코드, 발생 단계, 펌프 반응을 기록하면 다음 원인 분리에 사용할 수 있습니다.

## 검증 및 한계

공개 V4의 모듈 SHA-256 재현을 확인한 뒤 정확히 8바이트만 복원했습니다. 원본 ARM ILS 조회 입력/출력, 원본 압축 해제기의 전체 모듈 복원, 기존 유지보수 사용량/여유량 70개 호출, 다섯 외부 블록 합계, ZIP CRC/각 내부 파일 해시를 확인했습니다. 실제 펌프 구동·용지 감지·인쇄는 검증하지 못했습니다. OS와 하드웨어의 전체 동작을 검증한 결과가 아닙니다.

파일: `P10000_FM001PA_V4.5.EFU`

SHA-256: `2ec218b593e7a6cfb43accc71377c22b8acd2892ae5790064a4d1a5af98f7497`

재현: `python firmware/P10000/build_efu_research.py --ils-diagnostic`

V4.5는 사용자가 업로드를 승인한 기존 진단 EFU와 바이트 내용 및 SHA-256이 동일합니다. 이름만 변경했으며, 장치 내부 펌웨어 버전 문자열은 FM001PA로 유지합니다. 정품/잔량 100% 및 유지보수 가상화는 V4와 동일하게 유지합니다.
