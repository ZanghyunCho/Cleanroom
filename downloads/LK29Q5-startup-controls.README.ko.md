# LK29Q5 시작 화면 정지: 원본 동작 대조군 A/B

v3 실기 결과: 유지보수 카트리지를 장착해도 시작 화면이 지속됩니다.
터치음과 잉크 카트리지 도어 열림 안내는 동작하지만 모터·펌프 동작/소리는
관찰되지 않았다고 사용자가 보고했습니다. v3 이후에도 공식 원본 EFU로
되돌리면 정상 대기 화면까지 부팅된다고 사용자가 확인했습니다.

UI 응답은 일부 처리가 살아 있음을 보여줍니다. 구동부 제어 태스크/모듈의
상태나 초기화 대기 원인은 아직 확정할 수 없습니다. v2의 상태 7 강제 반환이
일부 상태 조회 함수를 비정상으로 만드는 것은 재현했지만, 그것만으로 실기
시작 화면 정지의 원인이 설명됐다고 볼 수 없습니다. v3도 같은 화면에서 정지했습니다.

**A/B는 원본 동작을 하는 대조군입니다. 잔량 100%·소비량 0·미장착 동작 패치는 없습니다.**
두 파일 모두 원래 공개키와 서명 바이트를 유지하고 선언 본문 길이는 실제보다 1 큽니다.
**후속 실기 결과: A와 B 모두 정상 작동했다고 사용자가 확인했습니다.**
이 환경에서 직접 관찰하거나 설치된 플래시를 읽어 확인한 결과는 아닙니다.

## 완료된 A/B 비교 순서와 해석

1. 공식 원본의 정상 부팅은 v3 이후에도 확인됐습니다. 유지보수 카트리지는
   장착하고 도어는 닫은 동일 조건을 유지합니다.
2. 공식 원본이 정상이라면 A를 시험합니다. 시작 화면 통과 여부와 구동부 동작을 기록합니다.
3. A가 정상이라면 B를 시험합니다. A가 멈추면 B 시험은 미룹니다.

| 관찰 | 다음 조사 범위 |
| --- | --- |
| 공식 원본도 현재 멈춤 | 펌웨어 본문 외의 유지 상태·장치 조건·초기화 원인부터 확인. A/B로 코드 탓을 단정할 수 없음 |
| 공식 원본 정상, A 정지 | 선언 길이/수신 완료/설치 후 상태 등의 경로. 기능 패치나 재압축을 원인으로 단정할 수 없음 |
| A 정상, B 정지 | 재압축 표현, 두 번째 프레임 이동, 실제 하드웨어 해제기, 부팅 무결성 처리 등 |
| A와 B 정상, v3 정지 | 변경된 실행 코드의 동작 또는 코드 변경에 대한 부팅 무결성 처리 등. 유지보수 로직만으로 원인을 단정하지 않음 |

두 파일을 정상적으로 업데이트할 수 있다는 실기 보장은 없습니다. 현재 정지 상태에서
공식 원본으로 복구하는 방법을 먼저 확보한 조건에서 구분 시험을 진행합니다.

## 소프트웨어 검증

- A: 원본 RCX와 다른 범위가 길이 필드 4바이트 안에만 있음을 확인. 서명 대상 본문은 원본과 동일하며 호스트 ECDSA 검사가 유효합니다.
- B: 재압축을 해제한 모듈과 원본 모듈의 바이트 차이 0. 원본 모듈 SHA-256은 `82c4c34f4ed5c1dd7118dd74839b499329d732d37b467df734ed5382a25dedac`입니다.
- B: 두 번째 프레임 바이트는 보존되지만 위치는 RCX `0x173a6c`에서 `0x17f51e`로 47,794바이트 이동합니다. 이 배치 변화도 대조 범위에 포함합니다.
- A/B: 네 섹션의 메타데이터 합계·본문 합계·내부 SHA-1, ZIP CRC와 재추출 바이트 비교 통과.
- A/B: 원본 ARM 본문 합계 함수를 사용해 첫 섹션 117,047,296바이트 검사 성공(1).
- B: 원본 로더의 기술자·DMA 정렬·LZ 재구성 통과. Huffman 완료 경계는 모델링했으며 실제 하드웨어 Huffman 처리는 검증하지 않았습니다.
- B: 본문이 바뀌므로 일반 ECDSA 검사는 유효하지 않습니다. 원래 서명 바이트를 유지한 것과 암호 검증 성공은 다릅니다.

이번 A/B 각각을 전체 ARM 상위 수신 함수에 다시 입력한 결과나 전체 부팅 시험은
아닙니다. v3의 RAM 함수 시험과 수신 시험이 실기 구동부 초기화 성공을 보장하지
않았다는 점 때문에 준비한 실기 대조군입니다.
