# P704 Stage 2 R1: 유지보수 기록 검증 플래그 복원

A/B에서는 없던 드라이버의 ‘인쇄중’ 표시가 Stage 1부터 발생하고, 대기열을 비운 뒤 재부팅해도 남는다는 사용자 보고를 조사했다. 원격지 프린터 본체 상태와 실제 드라이버 응답은 확보되지 않았다.

조사 중 Stage 1/2의 실제 코드 결함을 확인했다. 유지보수 필드 **0x49/0x4b를 near/full 사용량 플래그로 분류해 0으로 고정한 것은 잘못이었다.** 원본 기록 검증 경로는 이 두 필드가 모두 1인지를 검사한다. R1은 잘못 바꾼 명령 세 개를 원복한다. 드라이버의 ‘인쇄중’ 표시를 강제로 ‘준비’로 덮지 않는다.

## 재현한 결함

원본 초기화 함수 0x438b8e28(+0xb0e28)은 두 필드가 모두 1이 아니면 원래 setter를 호출해 1을 기록한다. 이후 원본 검증 함수 0x438b8cf4(+0xb0cf4)는 칩 전송 명령 0x14가 성공하면 원본 검사 0x438b8c7c(+0xb0c7c)를 실행한다. 그 검사는 읽기 명령 0x4e 이후 두 필드가 모두 1인지 확인하고, 그렇지 않으면 오류 분류 3·상세 0x53과 실패 반환 1을 만든다.

구 Stage 1/2에서는 getter 두 개와 setter를 모두 0으로 고정했으므로, 1을 기록하라는 요청도 0으로 처리되며 정상 전송 대조군에서도 이 검사를 통과하지 못했다.

| 같은 초기 RAM 및 정상 전송 모델 | 원본 | 구 Stage 1/2 | R1 |
| --- | ---: | ---: | ---: |
| 초기화 후 두 필드 | 1/1 | 0/0 | 1/1 |
| 검증 반환 | 0 | 1 | 0 |
| 오류 분류/상세 | 0/0 | 3/0x53 | 0/0 |
| 반복 20주기의 설정 호출 | 1회 | 20회 | 1회 |

반복 시험에서는 각 전송 주기 뒤 dirty 바이트를 비우고 같은 네이티브 함수를 다시 실행했다. 구 버전은 매번 설정을 다시 요청하고 실패했다. R1은 원본과 같이 최초 설정 후 다시 쓰지 않았다. 이 결과는 반복 동기화 결함을 입증하지만, 원격 드라이버의 ‘인쇄중’ 응답과 직접 연결한 물리 추적은 아니다.

## 수정 범위

Stage 2 대비 명령 3개, 실제 코드 바이트 7개만 원본으로 복원했다.

| RCX CROM 복원 모듈 오프셋 | 실제 주소 | 복원 |
| --- | --- | --- |
| +0xb1c5c | 0x438b9c5c | 필드 0x49 읽기 결과 보존 |
| +0xb1c7c | 0x438b9c7c | 필드 0x4b 읽기 결과 보존 |
| +0xb1c8c | 0x438b9c8c | 두 필드 setter의 원래 요청 인자 보존 |

유지보수 잔량 100%와 확인된 사용량 0 경로, 잉크 10개 슬롯의 Stage 2 변경은 유지한다. 인쇄 상태 설정/조회·NotifyIdle·JobStatus 코드 영역과 원본 기록 검증·오류 선택 코드는 변경하지 않았다. 통신 실패를 정상으로 처리하지 않는다.

## 시험

- 회계·칩 사용량 경계·보고·슬롯 분리 시험과 유지보수 회귀 총 1,295개 통과.
- 0x49/0x4b 시험은 ‘항상 0’이라는 이전의 잘못된 기대값을 원본 필드 입출력 보존으로 바로잡았다. 기존 시험 수치만으로 기록 검증이 정상이라고 판단한 범위가 부족했음을 이번 조사에서 확인했다.
- 새 원본/Stage 1/Stage 2/R1 비교 17개 통과: 초기 플래그 네 조합 × 쓰기/읽기 전송 성공·실패 네 조합 16개와 20주기 반복 시험 1개. 이미 유효한 경우 불필요한 전송을 하지 않는 원본 동작도 보존한다.
- 합계 **1,312개**. 오류 판정을 성공으로 바꾸는 훅은 없다. 전기적 칩 전송 완료 경계는 모델링하며 플래그 조작·검증·오류 기록은 원본 ARM을 실행한다.
- 최종 EFU 재추출 코드와 시험 코드 일치, ZIP CRC, 세 섹션 합계·SHA-1·경계, 공개키·서명 바이트, 두 번째 CROM 프레임과 복원 결과 보존 확인.

## 적용 및 남은 확인

기준은 동일한 P704 KH03P9.FY19이며 R1은 Stage 2를 포함한다. Stage 1로 되돌리는 파일이 아니다. 재부팅 후 작업을 보내지 않은 상태의 드라이버 표시와, 실제 출력 완료 후 유휴 복귀를 확인해야 한다.

**이 R1의 실제 설치와 드라이버 표시 해소는 아직 미검증이다.** 원본과 다른 반복 동기화 결함은 실행으로 재현·수정했지만, 보고된 표시의 유일한 원인이라고 확정하지 않는다. 물리 잉크/카트리지 존재·EEPROM 쓰기·전체 부팅은 이 ARM 시험의 범위 밖이다.

원래 공개키·서명 바이트와 실제 +1 선언 길이를 유지한다. 수정 본문의 일반 ECDSA 서명 검증은 예상대로 실패하며 ECDSA 성공 판정 패치는 없다.
